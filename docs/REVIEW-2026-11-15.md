# Проверка локальных изменений Masaki — 15 ноября 2026

Проверена разница `origin/main` (`283af8c`) → `37a858f`: 11 неопубликованных коммитов,
38 файлов, 3691 добавленная и 140 удалённых строк. Перед проверкой сделан `git fetch origin`;
рабочая папка, включая неотслеживаемые файлы, была чистой. Последний выпуск GitHub — v0.7.6.
Исходный `AUDIT-2026-11-15.md` использован как перечень заявлений для проверки.

Общий вывод: история и новые разделы менеджера паролей используют язык Masaki — общие
поверхности, палитру, скругления, типографику и кнопки. Однако считать весь набор готовым
нельзя: найдены ошибки сохранности данных, входа и интеграции новых функций. Зелёные
существующие тесты не проверяют несколько существенных конечных результатов.

## Исправления после проверки

Все 18 пунктов ниже исправлены по последующей просьбе пользователя. Описание находок сохранено
как состояние исходных коммитов на `37a858f`.

- CSV сохраняет секреты побайтно при обратном импорте; проверка повторов учитывает все сайты группы.
- Редактор получает полный адрес и сохраняет многострочную улицу. Изменения адресов/карт сразу
  обновляют интерфейс, их удаления передаются шифрованному сейфу как tombstone.
- Для автозаполнения main выдаёт токен конкретного документа, проверяет его origin перед отправкой
  и посылает секрет только выбранному фрейму. Через границы origin передаются только токен и
  геометрия; меню учитывает смещение iframe. Email-форма входа сохраняет предложения паролей.
- Conditional-вход открывает окно PIN; неверный код оставляет окно для повторной попытки.
- PRF и largeBlob возвращают двоичные JS-значения и отдельный JSON-формат; PRF с пустым объектом
  включает поддержку. Расширения объединяются, Signal принимает стандартные строки и возвращает
  Promise. Изменения largeBlob получают новую версию для синхронизации.
- Приложения используют локальную оболочку с webview и общими диалогами Masaki. Запросы идут в
  интерфейс своего окна; основной браузер открывается при необходимости. Сессия приложения не
  перезаписывает сессию браузера.
- USB/HID/Serial удерживают событие до ответа пользователя. Индивидуальные удаления истории
  хранятся в `history-removed.json`, синхронизируются и исключают возврат старых записей; свежие
  посещения показываются сверху.
- Поля given-name/family-name, section/shipping/billing, select и textarea поддерживаются.
- Вместо заголовков папок — одна плитка в общей сетке с четырьмя настоящими значками сайтов.
  Содержимое открывается рядом, меню адресует исходную закладку, перестановка двигает папку целиком.

Новые целевые проверки: `node scripts/review-regressions-test.mjs`,
`node scripts/review-ui-test.mjs forms|folders|apps`, `node scripts/review-sync-test.mjs`.
Синхронизация удалений проверена двумя настоящими профилями через подставной Google Диск,
включая повторное слияние и перезапуск второго профиля. PIN проверен также настоящим окном
Electron: неверный код → повторный ввод → успешная подпись. В скрытом cross-origin iframe
событие фокуса подаётся синтетически из-за отсутствия нативного hit-test OOPIF; заполнение,
адресация фрейма и координаты проверяются полностью.

Повторно проходят локальные сценарии `passkeys-test --local-only`, 23 границы паролей,
режимы passkey/autofill/history/display из audit-fixes-test, подставной Google вход и пауза
загрузок. Снимок новой папки — `test-output/review-fixed-folder.png`.
Физические USB/HID/Serial/Bluetooth и реальные сайты Google здесь по-прежнему не проверялись.

## Находки в исходных коммитах до исправления

### 1. [P1] Экспорт CSV повреждает пароли

`src/main/passwords.ts:168–174`: значения соединяются запятыми без заключения в кавычки.
Удвоение кавычек без внешних кавычек не делает CSV корректным. Дополнительный апостроф
для значений, начинающихся с `=`, `+`, `@`, `-`, тоже меняет секрет при обратном импорте.

Воспроизведено настоящими `exportTo` и `importCsv` на выдуманных данных:
`AA1,bb"cc` превратился в `AA1`; `=Abcdefghi123!` — в `'=Abcdefghi123!`.
Нужен экспорт с точным сохранением значений и корректным CSV-экранированием.

### 2. [P1] Редактирование адреса стирает его содержимое

`src/renderer/src/components/PasswordsPage.tsx:253–275` и
`src/main/autofill.ts:106–114`: API списка отдаёт лишь сводку, а редактор получает из записи
только имя. Все остальные поля он инициализирует пустыми, затем сохраняет как полную замену.
Открыть существующий адрес и нажать «Сохранить» достаточно для потери улицы, города,
индекса и контактов. Воспроизведено через настоящий интерфейс.

Нужно получать полную запись для редактирования и инициализировать все её поля.

### 3. [P1] Вход по ключу из автозаполнения обходит PIN

`src/main/passkeys.ts:657–662`: `useConditional` напрямую вызывает `doGet`, минуя `verifyPin`.
Проверка PIN есть только в `answer`, который обслуживает отдельное окно.
Воспроизведено на настоящем модуле: `pinSet() === true`, conditional-вход успешно выполнен,
PIN не передавался и окно не показывалось. Проверку нужно применять ко всем путям подтверждения.

### 4. [P1] Меню корневой закладки действует на другую запись после появления папок

`src/renderer/src/components/Chrome.tsx:549–558,603`: после фильтра `rootFavs` индекс `i`
больше не является индексом в `settings.favorites`, но именно его получает `openTileMenu`.
Перетаскивание также меняет первые N элементов исходного массива вместо выбранных корневых.

Воспроизведено с массивом `[закладка в папке, корневая закладка]`: правый клик по корневой
открыл меню закладки из папки. Удаление, цвет, форма и «Открыть» в таком меню затронут её.
Нужны исходные индексы или устойчивые идентификаторы и для меню, и для перестановки.

### 5. [P1] Пароль в iframe предлагается, но не подставляется

`src/main/index.ts:1267–1273` принимает origin дочернего фрейма, но
`src/main/passwords.ts:421–430` по-прежнему проверяет `wc.mainFrame.origin` и отправляет
`pw:fill` через `wc.send`, то есть главному фрейму. Идентификатор выбранного фрейма
теряется. Для другого origin будет ещё и отказ в проверке соответствия сайта.

В реальном same-origin iframe список появился, однако после выбора оба поля остались пустыми.
Меню также оказалось далеко от поля: `getBoundingClientRect()` из iframe не учитывает
смещение iframe в верхнем документе. Нужны адресация конкретного живого фрейма, повторная
проверка его origin перед отправкой и пересчёт координат. Аналогичная адресация нужна адресам и картам.
Текущий режим теста `iframe` проверяет только появление списка.

### 6. [P1] Окна приложений не обслуживаются менеджерами входа

`src/main/apps.ts:61–95`, `src/main/index.ts:1267–1269,2006–2010,2046–2051`:
приложение создаёт `BrowserWindow`, а `fromTab` принимает исключительно `webview`.
Поэтому наличие сессионного preload само по себе не даёт паролям и passkey работать в приложении.
В созданном через UI окне тестовый `navigator.credentials.create` вернул `SecurityError`.

При отдельном запуске с `--app=` ещё и отсутствует главное окно, через которое идут все
вопросы устройств, экрана, HTTP-входа и открытия вкладок. Нужна явная поддержка владельца
приложения/его диалогов; обещание об этих возможностях в исходном отчёте пока неверно.

### 7. [P2] PRF и largeBlob возвращают несовместимые с WebAuthn результаты

`src/main/passkeys.ts:511,533–535,562–564` и `src/preload/passkey-page.ts:91`:
PRF отдаётся как `{ first: "base64url" }` вместо структуры с `results.first` типа `ArrayBuffer`;
при регистрации отсутствует `enabled`. Двоичные данные largeBlob также остаются строками.
Обычный запрос регистрации с `prf: {}` вообще не включает поддержку PRF у создаваемого ключа.

Собственный тест читает `.prf.first` и поэтому принимает собственный неверный контракт.
Нужны правильные структуры для JS API и отдельная сериализация для `toJSON()`.
Контракт сверен с [WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/#prf-extension).

### 8. [P2] Signal API не принимает стандартные аргументы

`src/preload/passkey-page.ts:241–250`: API ожидает строки base64url, а обёртки передают
их в `enc`, который принимает только ArrayBuffer/View. `allAcceptedCredentialIds` ошибочно
обрабатывается как массив дескрипторов; у `signalCurrentUserDetails` используется
`userHandle` вместо `userId`. Методы возвращают `undefined` вместо Promise.

Вызов с корректным строковым `credentialId` воспроизведён: синхронный TypeError.
Текущий тест передаёт байты и проверяет нестандартный интерфейс.
Источник: [сигнальные методы WebAuthn](https://www.w3.org/TR/webauthn-3/#sctn-signal-methods).

### 9. [P2] Запрос largeBlob затирает PRF в том же запросе

`src/preload/passkey-page.ts:203–204`: два spread добавляют одно и то же свойство `extensions`.
Если запрошены PRF и largeBlob, второй объект заменяет первый. Перехват реального
сериализованного запроса подтвердил, что до main доходит только largeBlob.
Расширения нужно собирать внутри одного объекта.

### 10. [P2] Удаления адресов и карт не передаются другим устройствам

`src/main/autofill.ts:220–225`: `syncExport` выгружает только `liveA/liveC`, исключая tombstone.
Сейф синхронизации объединяет записи по id/t и сохраняет прежнюю запись на Диске;
другие устройства не узнают об удалении. Воспроизведено: после удаления экспорт содержит
ноль записей и ноль пометок удаления. Нужно экспортировать удалённые записи с новым t,
как уже делают пароли и ключи.

### 11. [P2] Список адресов и карт не обновляется после изменений

`src/renderer/src/components/App.tsx:179–180`: подписки на `autofill.onChanged` нет.
Списки в `AutofillSection` перечитываются только по `pwRev`, который меняют пароли и passkey.
В интерфейсе удалённый адрес оставался виден, хотя API уже возвращал пустой список.
Новая запись тоже не появится до повторного открытия страницы либо постороннего изменения пароля.

### 12. [P2] Адресное автозаполнение отменяет предложение логина у email-поля

`src/preload/guest.ts:187–190,263–270`: `focusin` запускает `offerFor`, затем `offerAf`.
Оба увеличивают общий `focusRequest`; `offerAf` отменяет ответ паролей даже когда адресов нет.
Воспроизведено с сохранённым логином и пустой адресной книгой: фокус email → 0 предложений,
фокус пароля → список появляется. Особенно мешает входу с клавиатуры/программным фокусом.
Нужно согласовать выбор режима и устаревшие запросы, сохранив предложения паролей.

### 13. [P2] Проверка повторённых паролей работает наоборот

`src/main/passwords.ts:156`: разные сайты приводят к `continue`, одинаковые — к предупреждению.
Воспроизведено: одинаковый пароль на двух разных сайтах → 0 замечаний; два аккаунта одного
сайта → 2 предупреждения «на другом сайте». Следует проверять множество сайтов всей группы,
а не только первые две записи.

### 14. [P2] Асинхронный выбор USB/HID/Serial не удерживает событие

`src/main/devices.ts:128–136`: обработчики сохраняют callback до ответа UI, но не вызывают
`event.preventDefault()`. Bluetooth в том же файле это делает.
В стандартном Electron chooser такой вызов нужен для собственного асинхронного выбора;
иначе стандартный отказ опережает ответ из интерфейса. Проверено по коду и официальным
[примерам Electron](https://www.electronjs.org/docs/latest/tutorial/devices); реальные устройства
не подключались. После исправления нужна отдельная проверка запроса и фактического подключения.

### 15. [P2] Удалённая запись истории может вернуться после синхронизации

`src/main/index.ts:1479–1483` только убирает запись локально; `syncHistory` объединяет списки
по url/time без пометки индивидуального удаления. Устройство с прежней историей вернёт
запись при следующем объединении. Нужны tombstone/версия удаления, а не только schedule.
Подтверждено анализом обеих веток слияния; отдельный прогон двух профилей здесь не выполнялся.

### 16. [P2] Заголовки папок не оформлены в стиле Masaki

`src/renderer/src/styles/app.css:7131–7143`: у `.fav-folder-h` не сброшены нативные фон и рамка.
На настоящем снимке тёмной темы — белая системная кнопка с серой рамкой посреди стеклянной панели.
Также отсутствует `fill: currentColor` у значка. Нужны фон/рамка из токенов и обычное поведение
интерактивных элементов Masaki. Это не субъективное отличие оттенка: используется системная поверхность.

### 17. [P2] История выводится от старых посещений к новым

`src/renderer/src/components/HistoryPage.tsx:139–159` сохраняет порядок массива хранилища,
который в main накапливается по возрастанию времени. При большой истории пользователь
сначала увидит самые старые дни, а сегодняшние окажутся внизу. Нужен обратный порядок
в представлении, без изменения массива хранилища.

### 18. [P2] Слишком узкий разбор полей адресной формы

`src/preload/guest.ts:260–287`, `src/main/autofill.ts:264–285`: вместо стандартных
`given-name`/`family-name` поддерживаются `fname`/`lname`; не разбираются группы
`section-* shipping/billing`, а `<select>` страны и `<textarea>` адреса не заполняются вообще.
Обычная форма заказа с корректными autocomplete-атрибутами поэтому останется частично пустой.
Текущий тест использует только простые `<input>` с одним токеном. Нужен разбор стандартного
autocomplete и заполнение соответствующих типов элементов.

## Изменения по дополнительным просьбам во время проверки

- Демонстрация экрана: видимые названия источников, название/номер монитора, основной монитор,
  разрешение, заголовок и значок приложения для окон. Исправлены гигантские SVG, которые скрывали
  подписи, и ширина сетки. Пустое превью не рисуется как сломанная картинка.
- Сведения о сайте: кнопка безопасности перед адресом, заметное предупреждение для HTTP,
  понятный статус в самой панели. Панель открывается под кнопкой в боковой панели либо над
  кнопкой в доке; убраны унаследованные одновременно top/bottom и горизонтальная прокрутка.
  На обычной высоте всё помещается без полос; при реальной нехватке высоты остаётся вертикальная.
- Загрузки: пауза/возобновление через настоящий DownloadItem, кнопки в поповере и на полной
  странице, состояние «На паузе», значок паузы в доке, остановка расчёта скорости/остатка.
  IPC ограничен главным интерфейсом. Отмена работает и во время паузы.

Пауза/продолжение относятся к живой загрузке текущего запуска. После закрытия Masaki прежняя
логика истории считает незавершённую загрузку прерванной и предлагает скачать снова;
восстановление DownloadItem после перезапуска в эту правку не входит.
